### 🔴 最優先(品質を一段引き上げる・本質的・即修正したい軽微なものはここではなく 🟡 へ)

#### [W4 要件粒度] F-1-1 のメンバー登録トリガーを LINE Webhook イベント名で確定させる
- **業界差分**: B5 LINE Messaging API リファレンスでは、友だち追加検知は `follow` イベント(Webhook)で受け取るのが標準。本要件では「友だち追加したアカウントを自動的に登録」と書かれているが、実装者が `follow` イベントで Webhook を受けるのか、定期ポーリングするのかが明示されていない。**IEEE 830 "unambiguous"** の観点で要修正。
- **参考事例**: LINE Messaging API リファレンス `https://developers.line.biz/ja/reference/messaging-api/#follow-event`
- **具体的改善案**:
```diff
  #### F-1-1. メンバー自動登録機能
- - LINE Bot を「友だち追加」したアカウントを、自動的にメンバーリスト(Google スプレッドシート)に登録する
+ - LINE Bot を「友だち追加」したアカウントを、Webhook の `follow` イベント受信時に自動的にメンバーリスト(Google スプレッドシート)に登録する
+ - LINE ユーザー ID + 表示名(`displayName`)+ 友だち追加日時を保存する
```
- **Why 🔴**: ここが曖昧だと Phase 1 着手 1 日目で実装者(=ユーザー本人)が手戻り。Phase 1 着手前に確定させる価値が極めて高い。

#### [W4 要件粒度] AC-8 の「1 サイクル完走」の具体的な時系列を明示する
- **業界差分**: B2 Wiegers の Acceptance Criteria は **Given-When-Then** 形式(例: "Given メンバー 4 名がメンバーリストに登録されている / When 管理者が質問配信コマンドを実行 / Then 4 名全員に Flex Message が届く")で書くのが業界標準。AC-8 の「1 サイクル完走」は粒度が大きすぎ、何をもって PASS / FAIL か実装者の判定がブレる。
- **参考事例**: Karl Wiegers "Software Requirements" 第 3 版 第 16 章 "Validating Requirements"
- **具体的改善案**:
```diff
- - [ ] **AC-8**: 上記 AC-1〜AC-7 が、エラーなく 1 サイクル(=友だち追加 → 質問 → 回答 → リマインド → 集計 → 通知)完走する
+ - [ ] **AC-8**: 以下の統合シナリオが完走する
+   - **Given**: メンバー 4 名が事前に友だち追加済 / 管理者がスプレッドシートに 7 候補日時入力済
+   - **When**: 管理者が「質問配信」コマンドを実行
+   - **Then**: 24h 以内に 4 名全員から回答が集まり(または未回答者にリマインドが送信され)、5 分以内に集計が完了し、結果通知が 4 名全員に届く
+   - **失敗判定**: いずれかの工程でエラーが発生 / 集計結果がスプレッドシート上の事実と異なる
```
- **Why 🔴**: AC-8 が MVP 完成判定の最重要 AC であるため、ここが曖昧だと「どこまでやったら完成か」の判定基準そのものが揺らぐ。
